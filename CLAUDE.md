# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Запуск и разработка

Локально (venv уже в репо):
```bash
source venv/bin/activate
uvicorn app:app --reload --port 8000           # веб-морда + API на http://localhost:8000
python3 daily_report.py --date 2026-04-17 --sub1 kub   # CLI-режим того же отчёта
```

В Docker (конфиг/output/logs монтируются с хоста, внешний порт 8001):
```bash
docker compose up -d --build
docker compose logs -f web
```

Healthcheck: `GET /api/health` → `{"ok": true}`.

Тестов и линтеров в проекте нет — проверка работы только через ручной запуск отчёта и сравнение с Google Sheets.

## Архитектура

### Единая точка сборки отчёта

`core.build_report(config, day, sub1)` — единственная функция, строящая дневной отчёт. Её дёргают три точки входа:
- `app.py` (FastAPI, `POST /api/report`) — веб-морда
- `daily_report.py` — CLI-обёртка
- `scheduler.ReportScheduler` — автозапуск каждого бренда в его собственное время по Европа/Самара за предыдущий день

`build_report` последовательно собирает пять внешних источников и опционально пишет в Google Sheets:

| Источник | Клиент | Что берём |
|---|---|---|
| VK Ads (через Ads Manager vktest2) | `ads_manager_client.py` | `GET /api/telegram/daily-stats?date=&all=true` — spent по ВСЕМ кабинетам пользователя (label не фильтрует с 2026-08-12) |
| Yandex Direct (через свой Ads Manager) | `yandex_client.py` | то же, но Яндекс |
| Яндекс.Метрика | `yandex_metrika_client.py` | `visits`/`pageviews`/`users` счётчика + достижения по списку целей |
| LeadsTech | `leadstech_client.py` | `data.summary` из `/v1/front/stat/by-subid` по `sub1`, **сумма по всем аккаунтам** |
| 8connect | `eightconnect_client.py` | `/api/report/list` → суммы cost/charge по `scheme_ids` |

Важный архитектурный принцип: **sheetsStat НЕ хранит VK/Yandex токены и список кабинетов**. Для VK/Yandex ходим в отдельные Ads Manager-ы (`kybyshka-dev.ru`, `yamanager.kybyshka-dev.ru`) по логину/паролю пользователя — JWT получаем через `POST /api/auth/login`, кабинеты привязаны к пользователю на стороне Ads Manager. Истёкший токен автоматически перевыпускается в `_get` (401 → relogin → retry).

Общая JWT-механика (login, _get с авто-relogin) живёт в `http_base.JWTAuthClient`; `AdsManagerClient` и `YandexAdsManagerClient` — тонкие наследники, добавляющие свой `get_daily_stats` (VK пробрасывает `label`, Yandex — нет). Одна общая функция `core._collect_ads_stats` обходит `accounts[]` и превращает ответ в унифицированный `{cabinets, total, errors}`.

### Несколько аккаунтов LeadsTech

У LeadsTech, в отличие от VK/Yandex, кабинеты **не** привязаны к одному логину, поэтому список аккаунтов хранится у нас: `leadstech.accounts: [{name, login, password, base_url?, sub1?, enabled}]`. `leadstech_client.build_leadstech_clients()` разворачивает его в клиенты (по одному на набор кредов); секционные параметры запроса — `page_size`, `strictSubs`, `untilCurrentTime`, `limitLowerDay`, `limitUpperDay`, `banner_sub_fields` — общие для всех аккаунтов. Пустой `base_url` в строке = общий `leadstech.base_url`, пустой `sub1` = общий `sub1` бренда.

`core.collect_leadstech` шлёт одинаковый запрос за день в каждый аккаунт и **складывает** аддитивные поля (`clicks/hosts/sum/raw_clicks/conversions/approved/rejected/inprogress`) — именно эти суммы уезжают в Sheets. `CR`/`AR` — проценты, их нельзя складывать: они пересчитываются из итоговых счётчиков (`_leadstech_ratios`). Разбивка по аккаунтам лежит в `leadstech.accounts[]` отчёта; упавший аккаунт даёт нули + `error` в своей строке и запись в `leadstech.errors`, отчёт при этом собирается с частичной суммой.

Обратная совместимость: если `accounts` пуст, аккаунт синтезируется из legacy-полей `leadstech.login/password` (+ env `LEADSTECH_LOGIN`/`LEADSTECH_PASSWORD`), поэтому старые профили работают без правок. Пароли аккаунтов маскируются в `GET .../config` и восстанавливаются из БД при сохранении через `app.SECRET_LIST_FIELDS` (сопоставление строк по `(base_url, login)`); обычный `SECRET_FIELDS` умеет только плоские секции.

### Хранилище — SQLite (`db.py`)

Всё состояние живёт в **SQLite** `data/sheetsstat.db` (env-override `SHEETSSTAT_DB`; том `./data` в compose). Без ORM — stdlib `sqlite3`, соединение на операцию, WAL, busy_timeout; схема через `PRAGMA user_version`. Таблицы:
- `profiles(id, config, sort_order, created_at, updated_at)` — весь конфиг бренда **одним JSON-блобом** (с секретами и `schedule` внутри); `name`/`sub1` в колонки не выносятся — источник правды один.
- `app_state(key, value)` — `active_id` и `default_schedule` (бывший манифест). Старые файловые функции `read_manifest`/`write_manifest`/`read_profile`/`write_profile`/`list_profile_ids` в `app.py` сохранили сигнатуры и стали адаптерами над `db.py`.
- `runs(profile_id, date, …, report)` PK `(profile_id, date)` — история прогонов, **upsert**: повторный прогон той же (даты, бренда) перезаписывает запись; упавший прогон (`report=NULL`) обновляет статус, но **не затирает** последний удачный отчёт (`COALESCE`). Пишется из одной точки `db.save_run` (ручной `POST /api/report` и планировщик; упавшие ручные прогоны тоже попадают в историю).
- `eightconnect_raw(date, data)` — дебаг-дампы сырого ответа 8connect (перезаписываются последним прогоном любого бренда за дату).

**Миграция**: при старте с пустой таблицей profiles `app.migrate_files_to_db()` одной транзакцией переносит `cfg/profiles.json` + `cfg/profiles/*.json` + `output/*.json` (rglob — покрывает и исторические подкаталоги от sub1 со слэшем) в БД. Файлы **остаются на диске как read-only архив** и больше не читаются/не пишутся; для повторной миграции достаточно удалить `data/sheetsstat.db`. Legacy `cfg/lt_vk_config.json` мигрирует, только если нет ни БД, ни файлов профилей; дальше он нужен лишь CLI `daily_report.py` (легаси: файловый конфиг, файловый вывод, в UI-историю не попадает).

### Конфиг и профили (бренды)

Каждый бренд — отдельный **профиль** (строка в `profiles`) со своим набором всех источников, `sub1`, `google_sheets.spreadsheet_id` и **своим расписанием** `schedule: {enabled, time}`. Профили редактируются через UI (`POST /api/profiles/{id}/config`). Схема задана pydantic-моделью `ConfigPayload` в `app.py`, дефолты для новых полей там же — старые профили не ломаются после обновления схемы.

Новый бренд проще всего завести **копией** существующего (`POST /api/profiles` с `copy_from`, или кнопка «копировать» в UI) и сменой `sub1` / `spreadsheet_id` / кредов. Раскладка таблицы у всех брендов одинаковая (см. sheets_writer), поэтому таблица нового бренда должна быть копией того же шаблона. При удалении бренда его строки в `runs` остаются — история переживает удаление.

`cfg/service_account.json` — Google сервисный аккаунт для Sheets, остаётся **файлом** (gspread открывает по пути из `google_sheets.service_account_json_path`). При `google_sheets.enabled=false` запись в Sheets пропускается, но отчёт всё равно собирается и сохраняется в БД.

### Семантический движок метрик (`metrics.py`) — источник правды по формулам

Все ~38 метрик описаны в реестре `metrics.METRICS` двумя видами: **base_service** (запрашиваются из сервисов, `source` — путь в отчёте типа `leadstech.clicks` или спец-ключ `metrika.goal`) и **computed** (мини-DSL выражение `expr`, например `"prihod - zatraty"`). Канонический layout — A..AK; колонки N «бекендер» и R «Долеты и Крот» эталона удалены 2026-09-02 (сдвиг на две колонки влево). **Миграция старых листов — руками**: удалить колонки N и R на всех месячных вкладках; у брендов с явным `cabinet_start_col`/`cabinet_max_col` сдвинуть их на 2 (kroko: AO/AU → AM/AS). Всё остальное следует за подписями строки 2. Одно выражение интерпретируется дважды: бэкенд-вычислителем (`compute_metrics`: None-семантика, деление на 0 → None) и генератором A1-формул (`expr_to_a1`: имена → буквы колонок листа, скрытая `lt_sumwebmaster` → инлайн-литерал, псевдопеременная `cabinet_spend` → сумма по кабинетным колонкам с коэффициентами). Реестр валидируется при импорте (парс, toposort, дубли подписей) — битый реестр валит старт. Формулы воспроизводят живую таблицу один в один (деления БЕЗ IFERROR — решение пользователя; в таблице возможен #DIV/0!). Оцифровка выверена по таблице Кубыхи: сверка `verify.py` (one-step: операнды формулы из ячеек листа, результат против ячейки) — август+июль 1186 ячеек 0 расхождений; июньские отличия — дрейф коэффициентов в самом листе.

`build_report` открывает `sheets_writer.open_sheet_context` ДО расчёта (оттуда значения ручных кабинетных колонок и окно строки), считает `report["metrics"]`/`report["metrics_meta"]` (`assumed_zero` — `cabinet_spend` без листа посчитан как 0; `coeff_warnings` — конфиг разошёлся со строкой 1; кабинеты отчёта без колонки в шапке warning'а не дают — они видны в `unmatched` сводки записи) и передаёт контекст в запись. `compute_cabinet_spend` предсказывает слагаемое кабинетов формулы D ровно как лист: сматченные колонки ← свежий spent отчёта, остальные (ручные AVITO/Google из `google_sheets.manual_cabinets`, нетронутые) ← текущие ячейки; кабинеты отчёта без колонки в шапке в сумму не входят (warning).

Формула «Прихода» с 2026-09-02 — `lt_sumwebmaster + manual_income` (полная сумма вебмастера LeadsTech инлайн-литералом, как в «Доходе с витрины», + ручные доходные поля); Приход СМС и «Клиенты» (AD, всё ещё пишется 0) в приход НЕ входят — доход вроде «Крота» заводится ручным полем с `target: "prihod"`. Ручные поля — `google_sheets.manual_cabinets: [{label, name, target}]` (legacy-строки нормализуются pydantic'ом; label — подпись колонки в кабинетной зоне листа, name — название в системе; управляются из вкладки «Метрики» кнопками +/✕; `target` — куда суммируется значение (коэф 1): "zatraty" (default, слагаемое формулы D) или "prihod" (доходное, слагаемое формулы C через псевдопеременную `manual_income`; без таких полей слагаемое исчезает из формулы — элизия пустых псевдо-сумм в `expr_to_a1`); доходные колонки исключаются из «Затрат» везде (запись, расчёт, генерация, сверка); удаление поля колонку листа не трогает; в `/api/metrics?profile_id=` отдаются как kind=manual_cabinet, значения строки — в `metrics_meta.manual_cabinets`); коэффициенты кабинетов для бэкенда/генерации — `google_sheets.cabinet_coeffs` (строка 1 живого листа главнее при записи; расхождение — громкий warning). Область кабинетной зоны редактируется per-brand: `google_sheets.cabinet_start_col`/`cabinet_max_col` (поля «Кабинеты: с/по колонку» в Настройках; пусто = AP..EZ; начало клампится до первой колонки после реестра (AL) — левее агрегатные колонки; резолв через `sheets_writer.cabinet_bounds`, используется везде: запись, расчёт метрик, генерация листов, сверка).

### Генерация листов (`sheet_builder.py`) и managed-режим

- `ensure_month_worksheet`: недостающая месячная вкладка создаётся с нуля из реестра (строка 1 — прочерки+коэффициенты, строка 2 — подписи+кабинеты, все даты месяца, формулы computed-колонок; ячейки ручных кабинетных колонок, «Прихода» и «Дохода с витрины» пусты — последние два пишутся прогоном с литералом sumwebmaster). Срабатывает **всегда** (с 2026-09-02, флаг `auto_create_tab` убран): `open_sheet_context` при отсутствии вкладки месяца генерирует её и продолжает запись; упавшая генерация — `error` в сводке. Вкладка сразу оформляется как эталонная таблица (спека `_format_requests` в sheet_builder, оцифрована с «Июль 26» LASDSDS и привязана к ключам метрик): сплошные границы, жёлтая шапка (зелёные СМС/витрина/кабинеты, оранжевый EPC, синий ROI), серые/светло-зелёные колонки данных, форматы чисел (проценты ROI, дата в A), ширины колонок; всё одним batchUpdate вместе с freeze.
- **Managed-режим** (`google_sheets.managed_formulas`): формулы всех computed-колонок строки даты генерятся из реестра при каждом прогоне (самовосстановление после ручных правок), строка-эталон 33 не читается. Плюс **итоговая строка** месяца (строка `3+дней_месяца`, оцифровка строки 34 эталона; реестр `metrics.TOTALS`: "sum" — SUM за месяц, "expr" — формула метрики от итогов (коэффициенты пересчитываются, не суммируются), "avg_pos" — AVERAGEIF>0 для EPC/ROI SMS/Маржи) — тоже переписывается каждый прогон по фактическим подписям (реордер-устойчиво), кабинетные и ручные колонки получают SUM автоматически; генерация вкладки создаёт её сразу (bold + жирная верхняя граница). Legacy-режим итоги не трогает. Legacy-режим (default, все старые бренды) — байт-в-байт прежнее поведение: клон строки 33 + 3 формулы. Отличия managed от legacy — только косметика (`F+G` вместо `SUM(F:G)`, скобки) и намеренное `U=AJ` (Adfox = Итого) вместо мусорной цепочки эталона через служебную колонку.
- Создание таблицы с нуля: у сервисного аккаунта **нулевая квота Drive** (политика Google) — `gc.create` падает; рабочий путь: пользователь создаёт пустую таблицу, шарит на сервисный аккаунт, вставляет ссылку и жмёт «Создать / разметить таблицу» → `POST /api/profiles/{pid}/sheets/init` генерирует вкладку и включает managed+auto_create. `POST .../sheets/create` остаётся для сред, где квота есть.
- API: `GET /api/metrics` (весь реестр + человекочитаемые формулы), `POST /api/sheets/verify {profile_id, tabs?}` — сверка формул с живым листом.
- Миграция брендов на managed — по одному: verify → `managed_formulas: true` → наблюдение. Пока все 9 живут на legacy.

### Google Sheets writer — самое специфичное место

`sheets_writer.py` пишет в таблицу «Копия kubyshka-zaim.ru» (у каждого бренда — своя копия одного шаблона):
- На каждый месяц отдельная вкладка вида `«Апрель 26»` (русские названия из `RU_MONTHS`); поиск — `find_month_worksheet`, без учёта регистра и пробелов («май 26» ≡ «Май 26»), чтобы автосоздание не плодило дубликаты. Отсутствующая вкладка **генерируется** из реестра (`sheet_builder.ensure_month_worksheet`, все даты месяца + формулы); если дата всё равно не найдена в столбце A — сводка возвращает `error`, запись пропускается.
- Даты — в столбце A в формате `dd.mm.yyyy`; столбец A — единственный позиционный якорь (первичный ключ строки).
- Агрегатные метрики привязываются **по подписям строки 2**, не по буквам: реестр `AGG_COLUMNS` = `{key: (каноническая подпись, номер вхождения, легаси-буква)}`. Дубли подписей разрешаются порядковым номером вхождения слева от зоны кабинетов («Приход» №1 = приход, №2 = charge блока СМС/8connect). Нестандартные подписи бренда переопределяются в профиле: `google_sheets.column_labels: {key: "подпись"}` (так живут kroko-2 и zanachkin). Промах подписи → метрика **не пишется** + warning в `header_warnings` сводки (тихого фолбэка на буквы нет; полный фолбэк на легаси-буквы — только если не разрешилась ни одна подпись, т.е. шапка сломана целиком). Легаси-буквы описаны в докстринге `sheets_writer.py`.
- Вся шапка (строка 1 — коэффициенты, строка 2 — подписи + имена кабинетов) читается одним запросом `A1:{min(EZ, col_count)}2` в `UNFORMATTED_VALUE` (формат ячейки округляет коэффициенты) и не кэшируется — свежая шапка на каждый прогон.
- Кабинеты — от фиксированной границы `CABINET_START_COL = AP` (= прежний AR минус две удалённые колонки; динамически определять ненадёжно — разметка строки 1 у брендов различается). По каждому `account_name` из `ads_manager.cabinets`/`yandex.cabinets` ищем колонку в шапке (`_find_header_column`: exact + префиксные эвристики) и пишем spent. Кабинеты без колонки в таблицу НЕ пишутся — видны в JSON-отчёте и в счётчике `unmatched` сводки.
- Формула «Затраты» = Σ(колонка кабинета × коэффициент из строки 1 над его именем; пусто/символ → 1) + слагаемые `ZATRATY_PLAIN_KEYS` без множителя. Формулы «Приход»/«Доход с витрины» строят ссылки на операнды тоже по разрешённым колонкам; формула с неразрешённым операндом не пишется целиком.
- Формулы клонируются из строки-эталона `TEMPLATE_ROW = 33` **только если это строка даты** (31-дневный месяц): в сгенерированных вкладках коротких месяцев в 33 стоит итоговая строка, её клон давал `=SUM(B3:B32)` в строке 01.09 и `#REF!` (баг 2026-09-02). Одну строку читаем через `ValueRenderOption=FORMULA`, кэшируем в `_TEMPLATE_CACHE` по `(spreadsheet_id, title)` и при вставке заменяем ссылки на 33 на номер реальной строки даты через `_TEMPLATE_ROW_RE`. Шаблонные формулы идут в batch первыми — явные записи их перекрывают, поэтому пропущенная strict-политикой метрика деградирует до шаблонной формулы.
- `write_daily_report(..., dry_run=True)` не пишет в таблицу и возвращает собранный batch в сводке — для дифф-проверок.

Если трогаешь layout — меняй вместе: `AGG_COLUMNS` ↔ подписи строки 2 во всех таблицах брендов (или их `column_labels`), строку-эталон 33 на всех месячных вкладках.

### История прогонов

- Прогон = строка в `runs` с полным JSON-отчётом; ключ `(profile_id, date)` (`profile_id`, а не `sub1` — sub1 у разных брендов может совпадать). API: `GET /api/reports?profile_id=` — метаданные (без тел), `GET /api/reports/{pid}/{date}` — сам отчёт.
- `output/` в docker-compose остаётся примонтированным только как архив старых JSON-файлов; новые прогоны туда не пишутся.

### Планировщик (APScheduler) — расписание на каждый бренд

`scheduler.py` (`ReportScheduler`) — обёртка над `AsyncIOScheduler`, стартует в FastAPI lifespan. У **каждого** профиля своё расписание `schedule: {enabled, time}` в его конфиге; планировщик регистрирует **по одному cron-job на бренд** (`report__<pid>`), у каждого своё время. Cron жёстко привязан к `ZoneInfo("Europe/Samara")` (UTC+4). В заданное время — `build_report(config, вчера, sub1)` только этого бренда, результат пишется как ручной `POST /api/report`: в `runs` (upsert) и в Sheets. «Вчера» — по Самарской дате (`datetime.now(SAMARA_TZ).date() - 1 day`), независимо от TZ контейнера.

`_profiles_provider()` отдаёт `(pid, config, sub1, schedule)` по всем профилям; `_effective_schedule` подставляет дефолт из `app_state` для профиля без блока schedule. `reload()` пересобирает набор job'ов (добавляет включённые, снимает выключенные/удалённые). При сохранении конфига/расписания (`POST /api/profiles/{id}/config` или `.../schedule`) дёргается `scheduler.reload()`; плюс watcher раз в 10с авто-перечитывает расписания из БД — ребилд/рестарт не нужен. Статус — `GET /api/schedule`: сводка (`enabled`, ближайший `next_run`) + `profiles[pid] = {enabled, next_run, last_run}`; `last_run` читается из `runs` (`db.get_last_runs`) и **переживает рестарт**. Ручной прогон — `POST /api/schedule/run-now {profile_id?}` (без тела — все бренды), трейс `trigger: "manual"` (у cron — `"cron"`, у мигрированных из файлов — `"import"`).

Зависимости в requirements: `APScheduler==3.10.4`, `tzdata==2024.2` (для ZoneInfo в docker-слим).

### Фронт

`static/index.html` + `app.js` + `app.css` — раскладка «**сайдбар брендов + рабочая область**», ходит только в `/api/*`. Слева список брендов с поиском, бейджем расписания (`⏰ HH:MM` / «выкл») и индикатором последнего запуска; снизу — кнопки создать/копировать/переименовать/удалить, плюс те же действия по **ПКМ на бренде** (контекстное меню адресуется конкретному бренду, не активному). Справа 5 вкладок: **Обзор** (дашборд всех брендов: тумблер расписания + время правятся прямо в таблице → `POST /api/profiles/{id}/schedule`, колонки next_run / последний запуск / «прогнать за вчера»), **Отчёт**, **Настройки** (скоупятся на выбранный бренд, включая карточку его расписания), **Метрики** (полный семантический реестр из `GET /api/metrics?profile_id=` тремя группами — запрашиваемые/ручные/вычисляемые, формулы read-only и рендерятся в системных именах бренда; редактируются: подпись колонки в таблице → `google_sheets.column_labels`, «название в системе» → `google_sheets.metric_names` (используется в блоке метрик отчёта и в формулах; `key` метрики — неизменный идентификатор, задел под редактируемые формулы), область кабинетов → `cabinet_start_col`/`cabinet_max_col`; сохранение — read-modify-write конфига, замаскированные секреты сервер восстанавливает из БД), **История** (с фильтром по бренду). Статика монтируется в FastAPI через `StaticFiles` **после** API-роутов (иначе SPA-маунт перекроет их).

## Конвенции

- Все внешние вызовы завернуты в `try/except` внутри `collect_*` функций `core.py`: ошибка одного источника не валит отчёт, она ложится в `result[<source>].errors` и рендерится в UI как warning.
- Все денежные/числовые значения из внешних API прогоняются через `_to_int` / `_to_float` — внешние сервисы любят слать строки и `null`.
- Даты в отчёте и в именах файлов — строго ISO `YYYY-MM-DD`. LeadsTech хочет `dd-mm-yyyy` — конвертация внутри `leadstech_client`.
- `spreadsheet_id` в UI можно вставить полным URL — нормализуется на входе через `_extract_spreadsheet_id` (валидатор pydantic).
